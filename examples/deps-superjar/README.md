# deps-superjar: Prolog inference inside the JVM, no JNI

One jar. `java -jar deps-superjar.jar` — that's the entire deployment
contract. No JNI, no native libraries, no GraalVM, no separate Wasm runtime
install. The jar runs anywhere a JVM runs.

This example takes the same `examples/deps.pl` the native and edge demos use,
compiles it with `plgc --target wasm32-wasi` (the **Tier 1** module — the
same `.wasm` `just wasm-smoke` runs under wasmtime), embeds it as a classpath
resource, and runs it on [Chicory](https://chicory.dev), a zero-dependency,
pure-Java Wasm runtime, shaded into the jar by Maven. Java talks to the
module through the **same wire contract as the native binary**: same flags,
same text output, same exit codes (0 no solutions · 1 solutions · 2 usage
error · 3 runtime error).

## Build and run

```sh
just deps-superjar        # plgc → deps.wasm; mvn shade → target/deps-superjar.jar
just deps-superjar-smoke  # equivalence gate vs the native binary

java -jar target/deps-superjar.jar --query "needs(app, X)"
#   X = auth / ui / crypto / render / crypto     (exit 1)
java -jar target/deps-superjar.jar              # no args: the showcase
```

The no-args showcase (`demo/Main.java`) is the integration point: Java owns
the questions and the reporting, Prolog owns the inference — transitive
closure, shared-dependency detection, a yes/no release gate, and the error
path, all observed from Java. `demo/Prolog.java` is the ~100-line wrapper to
copy into your own code: instantiate the module fresh per query (the
process-per-request model, minus the process) and read the exit code from
Chicory's `WasiExitException`.

## Why this matters

The JVM estate isn't going away. This is the third engine for one artifact —
clang/native, wasmtime, and now any stock JVM — which makes a compiled
patch-prolog program embeddable in a Java service as a *dependency*, not a
sidecar process: sandboxed by the Wasm model, observable by JVM tooling, one
portable jar.

## Measured numbers (this machine, Chicory 1.7.5 interpreter, Temurin 21)

| Query | native binary | wasmtime | superjar (Chicory) |
|---|---|---|---|
| `needs(app, X)` (deps.pl) | <0.01 s | <0.01 s | ~0.3 s incl. JVM startup |
| `count(1,000,000)` deep recursion | 0.6 s | 0.3 s | ~61 s |
| `count(5,000,000)` deep recursion | 5.2 s | 1.5 s | **traps after ~3.5 min** |

## The honest caveats

Chicory is correct but it is not a constant-stack, JIT-class engine, and the
gap is structural, not a bug:

- **Tail calls are desugared.** patch-prolog's codegen relies on Wasm tail
  calls (`return_call`) so that recursion and backtracking run in constant
  stack. Chicory supports the proposal *semantically* by rewriting
  `return_call` → `call`+`return` (the JVM has no tail calls), so **the
  constant-stack guarantee does not carry over**: deep recursion allocates
  real frames (heap objects) and gets slow, then dies. Measured ceiling
  above; wasmtime runs the same 5M-deep query in 1.5 s.
- **The interpreter is ~100–200× slower per inference** than native on
  recursion-heavy workloads. Chicory's [build-time/runtime
  compiler](https://chicory.dev/docs/usage/build-time-compiler) (Wasm → JVM
  bytecode) narrows this; we ship the interpreter because it's the
  zero-config default.
- **What this means in practice**: this surface is for *decision logic* —
  dependency graphs, release policies, linting — where queries are hundreds
  to thousands of inferences and the answer comes back in milliseconds. The
  default step limit (`PLG_MAX_STEPS`, 10k) already caps runaway depth on
  every engine. If a workload needs million-deep recursion, serve it from the
  native binary or a V8/wasmtime surface, which keep the constant-stack
  property.

## Layout

```
pom.xml                       # chicory + maven-shade → one jar, Main-Class demo.Main
src/main/java/demo/Prolog.java# the wrapper: load resource, run query, Result(exit, stdout, stderr)
src/main/java/demo/Main.java  # pass-through CLI + the no-args showcase
src/main/resources/deps.wasm  # GENERATED by `just deps-superjar` (gitignored)
```

Not wired into `just ci` / `just wasm-ci`: the base runners may not have a
JDK. Run `just deps-superjar-smoke` where java + mvn exist.
